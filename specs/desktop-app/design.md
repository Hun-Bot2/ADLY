# Desktop app: design

Implements `requirements.md` under ADR 007. The shell is Tauri (option A) or Electron (option B), decided by the DA-0
rule. Sections name "shell backend" for the Rust backend (A) or the Electron main process (B). Items marked *verify* must
be confirmed by a task before later tasks rely on them.

## 1. Processes and trust

```text
┌──────────── shell (Tauri/Rust or Electron main) ────────────┐
│ UI: bundled copy of hosted/public + new views (editor, repo,   │──invoke/IPC──▶ shell commands (allowlisted)
│     run, record/commit, sync, company, settings)               │
│ shell backend: engine supervisor · paths · repo/files · runner │
│                git · auth (OS store) · settings (state.json)   │
└───────────────┬────────────────────────────────────────────────┘
                │ spawn · /api/health · restart (backoff, max 3/min) · stop (graceful, then kill tree)
                ▼
 JS engine: hosted/local.mjs --api-only  ── node:sqlite ──▶ learner.sqlite3   (ONLY writer)
                                         ATTACH ro ──▶ catalog-vN.sqlite3, company-vK.sqlite3
 UI ── fetch http://127.0.0.1:<random>/api/* + X-App-Token ──▶ engine
```

- The UI is bundled with the shell; the engine serves only `/api/*`. The token is generated by the shell, passed to the
  engine via environment and to the UI via IPC. CORS allows only the shell origin.
- IPC commands are allowlisted (Tauri capabilities or Electron `contextBridge`). File access is limited to registered
  repositories and app data, after canonicalization (symlinks, `..`, and Windows short names and UNC paths rejected).
- In option B the engine runs as an Electron utility process with the same API boundary, so the code paths stay identical.

## 2. Ownership (ADR 007) and coordination

| Resource | Writer | Coordination |
|---|---|---|
| learner.sqlite3 | Engine only | Existing `BEGIN IMMEDIATE`, 5 s busy timeout, pre-migration snapshot |
| catalog / company layers | Build pipeline; installer copies | Attached `immutable=1` |
| Solution repo working tree and Git refs | Shell backend | Per-repository mutex; never runs while a `.git/index.lock` exists |
| Ingestion reads | Engine (`git log/show`, read-only) | Safe alongside shell writes; ingestion runs after the shell notifies "committed" and on its existing 5 s poll |
| Processes (engine, runs, git) | Shell backend | Process group (macOS) or Job Object (Windows) per child |
| Credentials | Shell backend | OS store via the `keyring` crate (A) or `safeStorage` plus the OS store (B) *verify* |
| App settings | Shell backend `state.json` (atomic write: temp file + rename) | Learning preferences stay in SQLite through the engine API |

## 3. Data layout

```text
<app-data>/learner.sqlite3, migration snapshots, backups/, explanations/
<app-data>/catalogs/catalog-vN/  (copied from the bundle on install/update, hash-verified)
<app-data>/catalogs/company-vK/  (same)
<app-data>/drafts/<repo-id>/…   <app-data>/runs/<run-id>/ (pruned after 7 days (P))   <app-data>/state.json
```

The engine gets the roots as arguments (`--database`, `--catalog-root`, `--company-root`); repository-relative defaults
remain for the CLI and development. The active catalog is still selected by the ledger's catalog switch. On first run with
an empty DB, the shell asks the engine to switch to the bundled catalog (existing `catalog use` logic exposed as an API).

## 4. Engine changes (minimal, all covered by existing tests)

- `local.mjs`: `--api-only`, token and CORS check, `/api/health`, root arguments, `POST /api/catalog/use`.
- `/api/local/daily-log/validate` (pure wrapper around `parseDailyLog`); `POST /api/local/ingest` (triggers one sync tick).
- Company: `company.mjs`, preference key, scope in `planProgressionV2` and `candidatePool`, `/api/company*` (company-prep design).
- Nothing else in policy modules changes; v1/v2 byte-identity tests guard this.

## 5. Runner

| Step | macOS | Windows |
|---|---|---|
| Toolchain | `python3`; `clang++`/`g++` | `py -3`/`python`; `cl` (Developer prompt env detection *verify*), `g++` (MinGW) |
| Isolation of tree | `setsid`; kill `-pgid` | Job Object with `KILL_ON_JOB_CLOSE` |
| CPU | `RLIMIT_CPU` | Job `PerProcessUserTimeLimit` |
| Memory | `RLIMIT_AS` not enforced on macOS *verify* → reported | Job `ProcessMemoryLimit` |
| Wall time / output | 5 s timeout; 1 MiB cap per stream; temp working dir per run | same |

Compile and run are separate steps with their own limits. Results: verdict per test (pass, wrong answer, runtime error,
timeout, output limit, compile error), time and exit code. The UI states that runs are not sandboxed.

## 6. Git, sync, auth

- System `git` CLI for every operation (as ingestion already does); minimum version detected. A bundled Git on Windows is
  decided in DA-W by measurement and licence review (Git for Windows is GPLv2).
- Commands: `init`, `clone`, `status --porcelain=v2`, `diff`, `add -- <paths>`, `commit -m`, `fetch`, `merge --ff-only`,
  `push` (no `--force`). Grep-enforced ban list: `--force`, `-f` on push, `rebase`, `reset --hard`, `commit --amend`, `filter-branch`.
- Sync state machine: `disabled → idle → {up_to_date | behind → ff | ahead → manual push | diverged → stop | error → stop}`;
  fetch at start and every 15 minutes (P) when enabled.
- Auth: GitHub device flow with a GitHub App client id (registered by the user; supplied in settings or the build
  config). The token is stored in the OS store and provided through `GIT_ASKPASS` (a helper binary reading from the shell
  over a pipe). The GitHub API is used only for the device flow and listing the user's repositories for clone.

## 7. Editor and views

CodeMirror 6 (Python, C++ modes); no LSP in v1 (P). New views: Repositories, Editor (file tree, tabs, drafts), Run/Tests,
Record & Commit (form → row preview → diff → commit), Sync, Company, Settings (toolchains, sync, sign-in, data folder,
backup). The existing views (journal, calendar, contests, mock contests, history) are reused unchanged and gain an "Open in
editor" action on recommendation slots.

## 8. Packaging and updates

- Option A: Tauri bundler (`.dmg` + `.app` notarized; NSIS or MSI with Authenticode); Node runtime included as a sidecar
  (single executable or binary plus scripts, per DA-0). Option B: electron-builder with the same signing.
- Shipped datasets: the active catalog version and its company layer, hash-verified on copy.
- Updates: the Tauri updater or electron-updater with signed manifests (design in DA-7); rollback = reinstall the previous
  build, and the newer-schema refusal protects data.

## 9. Testing

| Layer | Tests |
|---|---|
| Engine | Existing Node suite (unchanged) + token/CORS/health, daily-log validate, ingest trigger, company layer and scope |
| Shell backend | Unit/integration: paths (special characters), supervisor (crash, restart, quit), runner (per OS fixtures), repo (traversal), daily-log append (byte diff, CRLF), git (temporary repos + local bare remote), auth (mock device-flow server, fake credential store) |
| Cross-platform CI | GitHub Actions `macos-14` (arm64) and `windows-latest`: Node suite, shell tests, a packaged build (DA-W) |
| End-to-end | Scripted smoke against the packaged app (launch → journal → open problem → run → record → commit → recommendation refresh), plus a manual checklist with screenshots per OS |
| Regression | DR-I3 snapshot identity; Markdown files untouched except appended rows; real-catalog replay receipts reproduce |

## 10. Decisions and defaults

Gate: DA-0 (rule in ADR 007). Defaults, adopted unless the user changes them: DA-D2 CodeMirror 6; DA-D3 system Git; DA-D4
GitHub App, selected repositories only; DA-D5 Python 3 and C++17; DA-D6 manual push; DA-D7 explicit plus opt-in daily contest
sync; company defaults CP-D2–D5 (company-prep design §5).
